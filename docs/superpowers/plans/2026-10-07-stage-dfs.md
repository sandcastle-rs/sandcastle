# Stage DFS Implementation Plan

> **For agentic workers:** Use `superpowers:executing-plans` to implement this plan task by task. Steps use checkbox syntax for tracking. This request authorizes planning only.

**Goal:** Compute the stages required by a selected target, return their dependency-first execution order, and report reachable dependency cycles without recursive calls.

**Architecture:** Resolve Dockerfile references into a stage-indexed adjacency list, then run iterative three-color DFS from the target. Keep instruction lines on edges and retain the active path for cycle diagnostics. Use the resulting postorder directly for sequential stage execution.

**Tech Stack:** Rust 2024, MSRV 1.89, standard-library vectors; existing `anyhow` diagnostics at the planner boundary. No new dependencies or unsafe code.

**Spec:** The DFS approach discussed in chat on 2026-10-07 and Task 1 of [the multi-stage implementation plan](2026-10-05-multi-stage-dockerfiles.md).

## Scope and decisions

- This is the DFS portion of the stage planner, not the guest COPY or multi-stage executor implementation.
- A stage points to the stages it requires. Both stage inheritance through FROM and stage-backed COPY create edges. Context copies, scratch, and external images do not.
- Resolve and structurally validate references across all stages before traversal. The resolver, not DFS, handles duplicate names, unknown targets, numeric-reference bounds, and image references.
- Detect cycles only in the target's reachable subgraph. An unreachable cycle does not prevent an independent target from building. This makes the cycle-validation scope explicit where the broader plan currently says only "reject dependency cycles."
- Default target selection remains the final stage, performed by the resolver before DFS.
- Visit the FROM dependency first, followed by COPY dependencies in instruction order. Never derive traversal order from hash-map iteration.
- Retain repeated edges: each has its own instruction line. Completed dependencies are skipped, so each reachable stage appears once in the output.
- Exported layer selection remains the selected stage's completed descriptors; DFS does not traverse layers or determine which files COPY imports.

## Files and interfaces

Create `src/build/plan.rs` for graph resolution and traversal; register it with `pub mod plan;` in `src/build/mod.rs`. Keep traversal types private and its unit tests in the same file. Do not create a general-purpose graph crate.

```rust
struct Dependency { stage: usize, line: usize }
struct CycleEdge { from: usize, to: usize, line: usize }
struct DependencyCycle { edges: Vec<CycleEdge> }

fn execution_order(
    dependencies: &[Vec<Dependency>],
    target: usize,
) -> Result<Vec<usize>, DependencyCycle>;
```

Input invariant: the graph is nonempty, target is in bounds, and every edge index is in bounds. The resolver establishes these invariants; malformed Dockerfile input must produce resolver errors before this helper runs.

The traversal uses `Color::{White, Gray, Black}`, `Frame { stage: usize, next_dependency: usize }`, and vectors indexed by stage. Maintain the edge used to enter each active non-root frame, plus an active-position table for locating the beginning of a cycle. All arrays have graph-sized capacity; stack depth is bounded by the number of stages.

## Algorithm

1. Mark the target gray and push its frame.
2. Inspect the next edge of the top frame and advance its edge cursor before descending.
3. For a white dependency, mark it gray, record its entering edge and active position, and push a frame.
4. For a black dependency, continue; it already appears in the output.
5. For a gray dependency, extract only the active path beginning at that dependency, append the closing edge, and return a cycle error. Exclude any acyclic prefix leading into the cycle.
6. When a frame has no remaining edges, pop it, clear its active position, mark its stage black, and append that stage to the execution order.

Do not reverse the output: finishing dependencies before their consumers already produces execution order. Runtime is O(V + E), including graph-sized initialization; auxiliary memory is O(V). Cycle construction is O(cycle length) and occurs only on failure.
